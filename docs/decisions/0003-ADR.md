# 3. Architectural Decision Record

Status: accepted (Decisions 1-2, 8/20/26); Decision 3 proposed, not yet implemented

## Decision 1 - Decimal in Python

## Context
-- Municipalities sometimes use a base-10 decimal to calculate
ERU rates, while some round to the nearest half-increment or whole number.
-- Decimal allows for more precise calculations

## Decision
Decimal library over standard floating point arithmetic.

## Consequences
-- Pros: More exacting, more user-alterable, better for financial based calculation
-- Cons: Overall slower compared to built in float type


## Decision 2 - snake_case vs. camelCase in the API layer

## Context
-- API fields are consumed by both the Python/FastAPI backend and the
React/JS frontend. Python convention is snake_case; JavaScript/JSON convention
is typically camelCase.
-- Translating between naming conventions at the API boundary is a common
place for a field to be renamed on one side and missed on the other — the
same kind of rot `frontend/src/contracts.md` already exists to guard against.

## Decision
snake_case for the API fields since that is the Python standard. No
translation layer between frontend and backend; React consumes the fields
exactly as the backend emits them.

## Consequences
-- Pros: No mapping/translation layer needed in either codebase; fields stay
idiomatic on the Python side, where most of the domain logic lives.
-- Cons: Frontend code reads as non-idiomatic JS (snake_case keys in React
state/props) unless deliberately wrapped; a contributor used to camelCase
conventions could be tempted to "fix" this inconsistently if it isn't
documented.


## Decision 3 - On-site mitigation hydrology via EPA SWMM

Status: Proposed — targeted for the on-site mitigation/BMP costing milestone
(backlog, milestone 6+), not current scope.

## Context
-- `pervious.py` (MVP) compares pavement options on cost alone and cannot say
how much runoff a swap actually prevents — that requires real hydrology (a
design storm, soil/slope, infiltration behavior), which is why it was
deliberately left out of the MVP.
-- Two requirements from the original project brief are unaddressed without
this: calculating infrastructure costs to mitigate runoff, and modeling
future benefit under NOAA rainfall projections.
-- Known open risk already logged elsewhere: some utilities credit on-site
retention on the bill rather than reducing assessed impervious area. A
hydrology engine's runoff-reduction estimate is the only way to model that
correctly instead of guessing.

## Decision
Use EPA SWMM (public-domain, source-available) via the **pyswmm** Python
wrapper as the hydrology engine for this milestone. Model each property as a
SWMM subcatchment driven by a design storm — NOAA Atlas 14 IDF data for
present-day, a NOAA projection for the future-benefit comparison — and use
SWMM's built-in LID Controls module (Porous Pavement type) to get
runoff-volume and peak-flow reduction, instead of a cost-only comparison.
Isolate all of it behind a new `hydrology.py` module, the only door to
pyswmm/SWMM, mirroring how `rates.py` is the only door to `data/` — so the
pure core (`esu.py`, `pervious.py`) stays untouched and mockable.

Alternatives considered: `swmm_api` (lighter-weight, file-level `.inp`/`.out`
access, no run-control loop); `swmmrs` (newer Rust engine with Python
bindings, smaller ecosystem); a hand-rolled simplified runoff formula
(Rational Method or NRCS curve number) as a cheaper first cut — possibly kept
for the homeowner persona while full SWMM is reserved for the
developer/permitting persona, where precision matters more.

## Consequences
-- Pros: a defensible, engineering-grade answer to "how much less runoff" and
"how much more valuable under future rainfall," using the engine municipal
engineers already trust, instead of a cost-only proxy.
-- Cons: requires real civil-engineering inputs this project hasn't needed
yet (slope, Manning's roughness, soil infiltration, LID layer specs) — wrong
inputs produce confident-looking wrong answers, so this needs a dedicated
research/verification pass (the same discipline already applied to the ESU
rounding rule) before being built. Adds a native/C engine dependency to the
backend. SWMM runs take real wall-clock time, unlike the Decimal arithmetic
in the rest of the core, so `hydrology.py` must be treated as an I/O boundary
(timeouts, caching, mockable in tests), not folded into pure-core
assumptions.
-- Reversal trigger: if the parameter-gathering burden proves disproportionate
for the homeowner persona, fall back to a simplified runoff estimate there and
reserve full SWMM for the developer/permitting persona, rather than dropping
hydrology modeling entirely.
